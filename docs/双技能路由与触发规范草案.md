# 双技能路由与触发规范草案

## 1. 目的

当 `skill-stock-analysis` 与 `skill-tushare-servicehub-assistant` 同时安装时，需要降低“用户提示模糊导致技能误触发”的概率。

本草案只定义两者的职责边界、触发原则、追问机制与冲突优先级，不涉及代码实现细节。

## 2. 技能定位

### 2.1 `skill-tushare-servicehub-assistant`

定位为下层基础技能，承担两类职责：

1. TuShare 数据服务底座
2. 单专题场景分析

它当前已经覆盖的主要分析场景有：

1. 市场行情分析
2. 主营业务分析
3. 财务情况分析
4. 股权结构分析

这一层的核心特点不是“给出投资结论”，而是：

1. 先查本地仓库和缓存
2. 缺数据时再经 ServiceHub 远程补数
3. 输出结构化数据、摘要和单场景分析结果

### 2.2 `skill-stock-analysis`

定位为上层决策型技能，承担的是“多分析角色协同后的交易决策支持”。

它的核心模块不是单一专题，而是组合多个分析维度：

1. 基本面分析
2. 市场技术面分析
3. 新闻与舆情分析
4. 交易员结论
5. 组合经理最终裁决

这一层的核心特点不是“只取数”或“泛分析”，而是：

1. 综合多个维度
2. 形成一份面向投资动作的完整研报
3. 输出买卖建议、目标价、止损、持有周期与复核触发条件

## 3. 两个技能的本质区别

应避免把二者都笼统描述为“股票分析技能”。

更准确的区分应该是：

1. `skill-tushare-servicehub-assistant`:
   TuShare 数据与单场景分析底座
2. `skill-stock-analysis`:
   多分析师协同的交易决策技能

换句话说：

1. 下层技能解决“查什么、取什么、单项怎么解读”
2. 上层技能解决“是否值得买、怎么交易、如何给出投资动作建议”

## 4. 推荐路由原则

### 4.1 应优先路由到 `skill-tushare-servicehub-assistant` 的情况

当用户的真实意图更接近以下类型时，优先走下层技能：

1. 明确要查某类数据
2. 只关心某一个专题场景
3. 关注 TuShare 接口、字段、标准用例、自定义查询
4. 希望优先查本地数据库或缓存
5. 希望输出结构化数据或原始结果

典型请求特征：

1. “查一下”
2. “给我数据”
3. “看近三年财务”
4. “看前十大股东”
5. “查主营业务”
6. “跑一下 TuShare 用例”
7. “查接口字段”
8. “先查本地，没有再补”
9. “给我 JSON”

### 4.2 应优先路由到 `skill-stock-analysis` 的情况

当用户的真实意图更接近以下类型时，优先走上层技能：

1. 希望得到投资建议或交易建议
2. 希望知道值不值得买、卖、持有
3. 希望拿到目标价、止损、仓位、持有周期
4. 希望形成面向交易动作的正式研报
5. 希望由多分析角色支持最终投资决策

典型请求特征：

1. “投资建议”
2. “交易策略”
3. “买卖建议”
4. “值不值得买”
5. “该不该买”
6. “目标价”
7. “止损位”
8. “仓位建议”
9. “持有周期”
10. “多智能体”
11. “多分析师”
12. “TradingAgents”

## 5. 不建议使用单一技术词作为唯一触发条件

不建议把 `skill-stock-analysis` 的主要触发条件只设计成“多智能体框架”这一类技术词，原因如下：

1. 普通用户很少会主动使用这类术语
2. 用户更自然的表达通常是“给我投资建议”或“这只股票值不值得买”
3. 如果只靠技术词触发，会导致上层技能在真实对话中命中率偏低

因此，更合理的做法是：

1. 以“是否要交易决策”为主
2. 以自然表达为主
3. 以技术词为增强触发，而不是唯一触发

## 6. 模糊请求的处理机制

### 6.1 存在混淆风险的典型提示

以下提示天然有歧义，不应直接武断选择技能：

1. “帮我看看美心翼申”
2. “分析一下某某公司”
3. “了解一下这家公司”
4. “研究一下某某”

这类提示默认更接近“了解公司基本情况或单项情况”，不应直接路由到交易决策技能。

### 6.2 建议追问策略

当用户提示无法明确区分“单专题数据分析”还是“综合投研研报”时，应先追问一次，并且只追问最小必要问题。

推荐追问模板：

`你是想了解这家公司的基本情况，还是想让我直接给出投资建议或交易建议？`

如果用户回复偏向公司情况、经营、财务、行情、股权等事实分析，则走 `skill-tushare-servicehub-assistant`。
如果用户回复偏向投资判断、买卖建议、交易策略，则走 `skill-stock-analysis`。

### 6.3 追问原则

1. 只问一次最关键的分流问题
2. 不要一次性把所有参数都抛给用户
3. 在已能从上下文推断的前提下，不重复追问

## 7. 冲突时的默认优先级

如果运行环境要求“尽量少追问”，必须在模糊情况下直接选择一个技能，则建议采用以下默认顺序：

1. 先判断用户是否在要“结论”
2. 再判断用户是否只在要“数据/单专题”

具体优先级建议如下：

1. 出现“投资建议、买卖建议、策略、目标价、止损、仓位、值不值得买”时，优先 `skill-stock-analysis`
2. 出现“接口、字段、用例、JSON、本地缓存、行情数据、财务数据、股东数据、公司情况”时，优先 `skill-tushare-servicehub-assistant`
3. 如果两类词都没有，只是泛泛说“看看/分析一下/了解一下”，默认优先 `skill-tushare-servicehub-assistant`

如果确实不能追问且必须自动执行，建议默认优先下层技能，原因如下：

1. 下层技能成本更低
2. 下层技能风险更小
3. 下层技能先给事实，再升级到综合研判更稳妥
4. 上层技能属于更重、更贵、且直接导向交易动作的能力

## 8. 两个技能在文案上的建议区分

### 8.1 对 `skill-tushare-servicehub-assistant` 的建议表述

建议在 `SKILL.md` 或 `README.md` 中强化以下表述：

1. TuShare 数据底座
2. 单场景专题分析
3. 优先本地仓库与缓存
4. 输出结构化数据、summary、report、analysis_text
5. 适合行情、主营、财务、股权结构等专题查询

不建议只写：

1. 股票分析
2. 公司分析

因为这样的描述会和上层技能发生明显重叠。

### 8.2 对 `skill-stock-analysis` 的建议表述

建议在 `SKILL.md` 或 `README.md` 中强化以下表述：

1. 多分析师协同
2. 面向交易动作的研报
3. 投资建议与交易建议
4. 目标价、止损、仓位、持有周期
5. 面向最终投资决策

不建议只写：

1. 综合分析股票
2. 看看某只股票怎么样

因为这样的描述过于宽泛，也会和下层技能争抢入口。

## 10. 结论

这两个技能不应通过“是否带分析功能”来区分，因为两者都带分析能力。

更合理的区分方式是：

1. 下层技能负责数据、公司情况与泛分析
2. 上层技能负责交易建议与投资决策
3. 模糊请求默认先按下层技能理解，必要时追问一次
4. 只有当用户明显要求投资动作建议时，才触发上层技能

这套边界如果在文案、示例和路由逻辑中保持一致，两个技能同时存在时的混淆会显著下降。
